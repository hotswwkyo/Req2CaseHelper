### 改动 A：回补 4 项需求完整性检查（P0 + P1）

**位置**：`.github/agents/TestDesigner.agent.md` 技能一 · 步骤 3

**插入锚点**：现有 `c. **操作流程完整性检查**` 代码块的最后一行（`- 取消后状态不变`）之后、`**每个测试点必须包含**：` 之前

**拟插入文本**（可直接粘贴）：

```markdown
   d. **列表项挖掘**：需求中的列表项（List Paragraph）可能包含独立功能点，不可视为纯描述性文字。
      - 操作方法：逐行扫描所有列表项，对每一项自问"这是一个独立的功能点吗？"
      - 判据：该项虽挂在某功能点之下，但其本身描述了可独立操作/查看/记录的功能 → **必须独立成测试点**。

   e. **概览树交叉比对**：需求开头的"模块概览树"是结构索引，不是完整清单。
      - 操作方法：列出概览树后，逐项对照详细需求中的每个标题与列表项。
      - 判据：详细需求中存在、而概览树未列的条目 → **必须补入测试点清单**。

   f. **空洞内容标记**：遇到"规则如下""说明如下""包括："等引导词，但其后**无实质内容**（表格/图片未解析、文本整理遗漏）时，标记为 **【待澄清】**，不得当作"无此需求"而忽略。
      - 操作方法：全文搜索"如下：""包括：""说明：""规则："等引导词，逐一确认其后是否有实质内容。

   g. **条件分支穷尽**：需求中出现 **"或 / 且 / 如果…则 / 当…时"** 等条件描述时，必须穷尽所有分支。
      - 操作方法：将条件转换为**判定表 / 真值表**，逐行检查每个分支是否有测试点覆盖。
      - 判据：**同一条件的不同满足方式也是独立场景** —— 即使多个子条件指向同一结果（如"均为已发布**或**已生效**或**已失效"），每个子条件也须独立成测试点，因为前置状态不同、代码路径可能不同。
```

**理由**：这 4 项在 `备份/` 版中均附带真实教训案例，且**与当前版 3 项检查零重叠**，加回不会产生规则冲突。

**去噪处理**：原文的教训案例含上一项目的专有编号（`TP-PM-024`、`TC-FM-006`、`表单操作日志`、`关联创建/变更关联`），跨项目复用属噪音且可能误导模型，故**只保留"操作方法 + 判据"，删除专有案例**。

### 改动 B：功能原子性（测试点级）（P2）

**位置**：技能一 · 步骤 3，紧跟 g 之后

**拟插入文本**：

```markdown
   h. **功能原子性（测试点级）**：每个测试点只验证**一个独立测试目标**（用例级规则见核心原则「一场景一用例」）。
      - 操作方法：检查测试点描述是否含"和 / 与 / 及"等连接词，若是则判断子功能是否独立可拆。
      - ❌ **应拆分**：搜索 + 排序（分属不同功能）；功能 A 正向 + 功能 B 正向；同一断言在**不同状态**或**不同业务对象类型**上各验证一次。
      - ✅ **可合并**：同一功能的多个输入条件（如"按编码搜索 + 按名称搜索"）；同一业务流程的连续步骤。
```

**理由**：备份版检查 5 的第三条判据"同一断言在多个不同**状态**下各验证一次 → 即使预期相同也应拆分"**在精神上可直接外推到"多个业务对象类型"**，但原文只写了"状态"，模型不会自动外推。本改动补上该外推，并保住原有"和/与/及"判据。

**可选项**（需你确认，默认不加）：在 h 末尾补一句判定信号——
> 判定信号：测试点或用例的**步骤/预期**中出现"逐类 / 分别 / 各自 / 均 / 所有 / N 类 / N 个"等集合或计数表述，即为拆分信号。

> 📌 该句属"阶段三（用例层）"的性质，为尊重本轮范围默认**不加**，留待第二轮一并处理。

### 改动 C：「一场景一用例」条款追加一句（P2）

**位置**：核心原则 · 「一场景一用例（强约束）」条款**末尾**

**锚点**：该条现有结尾为 `……例如"分别尝试A/B/C三种场景"的写法违反此规则，必须拆为三条独立用例。`

**拟追加文本**：

```markdown
  **同一断言在多个不同业务对象类型（N 类申请 / N 种单据 / N 个入口）上各验证一次时，即使预期结果完全相同，也必须逐类拆为独立用例**——与"不同状态必须拆分"同理。
```

**理由**：这是**唯一直接命中 `TC-FLOW-019` 形态**的条款。原规则的示例只枚举了「等价类 / 边界值 / 异常类型 / 角色」，未包含"多个业务对象类型"，导致"会签顺序调整"可被合法理解为**一个**场景、14 类只是其数据变体，于是合并反被当作"遵守一场景一用例"。
